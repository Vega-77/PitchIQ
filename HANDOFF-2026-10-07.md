2. **Resumable long runs.** Make long runs work in **5-minute chunks** that skip

3. **Temp-folder safety.** Ensure nothing a long run needs lives in `%TEMP%`.
   Scratchpad files have vanished before, probably to Windows temp cleanup.
4. Re-run pytest: all green.

### Step 2: Faster ball + camera pass, without making the ball worse
1. **Profile `drun.py`.** Measure registrar vs candidate detector vs ranker per
   frame, in-situ over 40+ frames: short benchmarks on this machine vary 3x.
2. **Try, one at a time:**
   - fewer candidates scored per frame;
   - bigger GPU batches or fewer processes (GPU ~75% idle);
   - camera registration every Nth frame with interpolation (the camera pans
     slowly);
   - shorter or cheaper TAPNext bridging (`TNS=384`, skip more gaps).
3. **Accuracy gate.** Each speed-up is kept only if the Hybrid 90 scores are
   unchanged on the existing ball labs: `score2d.py`, `score3d.py`,
   `build_report.py` against the bar in §4. Wrong picks are judged first. If a
   speed-up costs accuracy, show the user the trade-off before choosing.

   that can't be reached cleanly, tell the user what is realistic.
5. Then ask the user before the long dev runs.

### Step 4: Automatic checks (no labels needed)
Build as a repo module with tests, per game and per stretch:
- **Calibration health:**
  - share of painted-line pixels within 1.5 m of the model's lines, over time
    (drift as the match goes on);
  - far/near player-height ratio.
- **Map physics:**
  - player speed > ~10 m/s, teleports, acceleration tails;
  - more than 11 per team on the pitch;
  - anyone classed "player" standing still outside the lines;
  - team flips per identity;
  - ID fragment counts.
- **Ball physics:**
  - impossible speeds;
  - flights that don't start or end near a player;
  - share of frames with a ball during play vs dead balls.
- **Stability:** jitter of map dots; agreement of jittered repeats.
- **Validate the checks first.** On the dev labels (fm01, fr00, vid1, ball
  truthdb), confirm each check fires where the real errors are. Drop any check
  that does not track real errors.

### Step 5: Spot-check lab (yes/no questions, no marking)
1. **Platform.** A published Artifact with the `db` capability, like the
   fm01/vid1 labs. Clone `data()` before editing, since db snapshots are
   frozen, and test against a freezing mock db.
2. **Question format.** One highlighted thing per question, shown as the real
   frame, a zoomed crop and a 2-second clip. Every question has **"can't tell"**.
3. **Keys and pacing.** Keyboard keys 1/2/3 at ~3 s per answer. Progress saves,
   so the user can stop anytime. Sittings of ~200 questions (~10 min).
4. **Question types:**
   - player / off / referee?
   - which team? (show kit swatches)
   - same person 1 second later?
   - are the drawn lines on the painted lines?
   - is someone here missing a ring?
   - is the ring on the ball?
   - is the ball visible with no ring?
5. **Answerability.** If a type gets >15% "can't tell" on the first dev run,
   redesign or drop it.
6. **Volume.** About **400 answers per question type per game**: at a 10% error
   rate, 150 answers give only ±5% and 400 give ±3%. The user wants plenty of
   data (underfitting worry), not less.
7. **Dev answers are training and tuning data.** Over-sample cases where the
   model is unsure, since they teach most. **Scores come only from the
   randomly sampled questions.**
8. **Rollout.** First run one dev game (e.g. East Brunswick) to confirm every
   type is answerable, then as many dev sittings as the user wants.
